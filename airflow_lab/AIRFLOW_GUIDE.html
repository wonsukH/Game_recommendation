1. Airflow가 맡는 일

이 프로젝트의 배치는 원래 scripts/daily_crawl.bat과 crawl_watchdog.ps1로 돌았다. 서빙 산출물 재빌드는 docs/operations.md §7에 다섯 줄짜리 명령 목록으로 적혀 있고, 사람이 순서대로 친다. 이 방식으로 안 되는 것이 네 가지다.

항목bat 파일로는
의존성순서대로 적을 수는 있다. 중간이 실패해도 뒤가 그냥 실행된다.
부분 재시도5단계 중 3번째만 깨졌을 때 3번부터 다시 돌리려면 손으로 한다.
이력어제 성공했는지, 각 단계가 몇 초 걸렸는지, 언제부터 깨졌는지 남지 않는다.
관측지금 돌고 있는지 죽었는지 알려면 프로세스 목록을 뒤진다.

Airflow는 이 넷을 맡는다. 계산을 대신 해주는 물건이 아니다. 연산은 여전히 원래 스크립트가 하고, Airflow는 언제 무엇을 어떤 순서로 부를지, 실패하면 어떻게 할지, 그 결과를 어디에 기록할지만 관리한다. 처음에 제일 헷갈리는 지점이라 먼저 못 박아 둔다.

실행되는 명령 자체는 새로 만든 것이 아니다. DAG 로그에 찍힌 첫 태스크의 명령줄은 이렇다. 

Running command: ['/usr/bin/bash', '-c',
  'python -m pipeline.game_rec.data.behavioral_extract --out /opt/project/outputs/p5']

operations.md §7의 첫 줄과 같은 명령이다. Airflow가 대신 쳐준 것뿐이다.

2. 구성 요소

Airflow는 한 덩어리가 아니라 역할이 나뉜 여러 프로세스다. 그래서 컨테이너를 여러 개 띄운다.

스케줄러

두뇌에 해당한다. dags/ 폴더를 주기적으로 읽어 DAG 파일을 파싱하고, 실행할 때가 된 것을 고르고, 의존성이 충족된 태스크를 실행 대기열에 넣는다. 우리 설정은 15초마다 폴더를 다시 읽는다 (AIRFLOW__SCHEDULER__DAG_DIR_LIST_INTERVAL: 15).

메타데이터 DB

Airflow의 기억 저장소다. DAG 목록, 실행 이력, 각 태스크의 상태와 시각, 재시도 횟수가 전부 여기 들어간다. 우리는 PostgreSQL 16을 쓴다.

추천 데이터인 data_collection/steam.db와는 아무 관계가 없다. 이름이 둘 다 DB라 헷갈리는데 완전히 별개다. Airflow 메타DB를 통째로 날려도 추천 데이터는 멀쩡하고, 반대도 마찬가지다.

웹서버

http://localhost:8080. 메타DB를 읽어서 보여주기만 한다. 웹서버를 꺼도 파이프라인은 그대로 돈다. 계정은 admin / admin이다.

Executor

컨테이너가 아니라 스케줄러의 설정값이다. 태스크를 어떤 방식으로 실행할지 정한다.

종류동작비고
SequentialExecutor한 번에 하나SQLite 메타DB일 때의 기본값. 병렬 불가
LocalExecutor같은 머신에서 여러 프로세스이 프로젝트의 설정. 진짜 DB가 필요해서 postgres를 띄웠다
CeleryExecutor여러 워커 머신에 분산실무
KubernetesExecutor태스크마다 파드 생성실무

LocalExecutor를 골랐기 때문에 build_ease_artifact와 build_catalog_db가 실제로 동시에 돌았다. SequentialExecutor였다면 하나씩 돌았을 것이다.

4. 마운트 설계

Airflow 문법이 아니라 안전 설계다. docker-compose.yaml의 이 세 줄이 핵심이다. 

volumes:
  - ../:/opt/project:ro                                 # 리포 전체, 읽기 전용
  - ./work/outputs:/opt/project/outputs                 # 그 안에 rw로 겹침
  - ./work/serving_data:/opt/project/serving/data       # 그 안에 rw로 겹침
  - ./work/p6_ood:/opt/project/experiments/p6_ood       # 그 안에 rw로 겹침

p6_ood 오버레이는 p5_validate가 판정 결과를 experiments/p6_ood/p5_validate.json에 쓰기 때문에 있다. 같은 디렉터리에 동결된 P6 패널이 들어 있는데 되돌릴 수 없는 증거 파일이라, 실제 디렉터리에 쓰기 권한을 주는 대신 사본을 주고 p6_panels.json만 씨앗으로 넣는다.

읽기 전용 마운트 안쪽에 쓰기 가능 마운트를 겹쳐 넣은 구조다. 파이프라인 스크립트들이 출력 경로를 REPO_ROOT / "outputs"처럼 자기 파일 위치 기준으로 계산하기 때문에, 이렇게 하면 프로젝트 코드를 한 줄도 안 고치고 모든 기본 경로가 스크래치로 떨어진다.

왜 이렇게까지 하냐면 serving/data/의 16개 파일이 git으로 추적되고 배포된 Streamlit 앱이 읽는 실물이기 때문이다. 파이프라인을 잘못 돌려 거기 덮으면 라이브 서비스 품질이 내려간다. DAG 코드에 실수를 해도 컨테이너에서 물리적으로 도달할 수 없게 만드는 편이 안전하다. 확인한 결과는 이렇다. 

$ touch /opt/project/__should_fail
touch: cannot touch '/opt/project/__should_fail': Read-only file system

$ ls /opt/project/serving/data
ease  tag_vocab.json        # 실제 catalog.json, index_maps.json 등은 목록에 없음

SQLite를 쓰지 않는 이유

steam.db도 같은 read-only 마운트 안에 있다. 읽기는 실제로 검증했다. 컨테이너에서 public=1 AND complete=1 유저 수를 세면 23,347이 나오고, 호스트에서 센 값과 같다.

쓰기는 막았다. SQLite의 WAL 모드는 공유 메모리 파일(-shm)을 mmap해야 하는데, Windows 드라이브를 컨테이너에 붙일 때 거치는 9p 파일시스템에서 이게 보장되지 않는다. SQLite 공식 문서가 네트워크 파일시스템에서 WAL을 지원하지 않는다고 명시한다. 읽기 실패는 다시 하면 되지만 쓰기 실패는 2GB짜리 원본을 잃는 일이라 층이 다르다.

5. 핵심 개념

DAG

Directed Acyclic Graph, 방향성 비순환 그래프. 파이프라인의 정의다. 파이썬 파일 하나가 DAG 하나다. 비순환인 이유는 A에서 B로 갔다가 다시 A로 오는 순환이 있으면 영원히 끝나지 않아서다. DAG 파일은 실행 계획서일 뿐 그 자체가 실행이 아니다.

Task와 Operator

DAG 안의 작업 단위 하나가 Task다. Operator는 그 Task의 종류다.

Operator하는 일
BashOperator셸 명령 실행. 이 프로젝트는 전부 이것을 쓴다
PythonOperator파이썬 함수 호출
SSHOperator원격 서버에서 명령 실행
DockerOperator컨테이너를 띄워서 실행
EmptyOperator아무것도 안 함. 그래프 구조용 표식

기존 스크립트가 이미 CLI로 완성되어 있으면 BashOperator가 맞다. 파이썬으로 감싸면 임포트가 스케줄러 파싱 시점에 일어나서 오히려 문제가 생긴다.

DAG Run

DAG를 한 번 실행한 인스턴스. 우리가 돌린 것의 ID는 manual__2026-08-02T05:21:46+00:00이다. 같은 DAG를 어제도 오늘도 돌리면 DAG Run이 두 개 쌓인다. 이력이 여기서 나온다.

Task Instance와 상태

(Task × DAG Run) 조합이다. "오늘 실행의 behavioral_extract"가 Task Instance 하나다.

상태의미
queued실행 대기
running실행 중
success성공
up_for_retry실패했고 재시도 대기
failed재시도까지 다 쓰고 최종 실패
upstream_failed앞 태스크가 실패해서 시작조차 안 함
skipped건너뜀

upstream_failed가 bat 파일에 없는 동작이다. 앞이 깨지면 뒤가 자동으로 멈춘다.

6. DAG 파일 해부

airflow_lab/dags/p5_rebuild.py를 위에서부터 본다.

공통 설정

default_args = {
    "retries": 2,
    "retry_delay": timedelta(minutes=1),
    "execution_timeout": timedelta(minutes=45),
}

모든 태스크에 적용된다. retries: 2는 최초 시도에 재시도 2회를 더해 최대 3회다. 로그에 Starting attempt 1 of 3이 찍히는 것이 이 설정이다. execution_timeout이 없으면 멈춘 태스크가 영원히 실행 슬롯을 잡고 있는다.

DAG 선언

with DAG(
    dag_id="p5_rebuild",
    start_date=datetime(2026, 8, 1),
    schedule="0 12 * * *",
    catchup=False,
    max_active_runs=1,
    default_args=default_args,
    tags=["game-rec", "p9"],
) as dag:

tags는 UI에서 DAG를 필터링하는 라벨이다. DAG가 수십 개가 되면 필요해진다. 나머지는 7절에서 다룬다.

태스크

extract = BashOperator(
    task_id="behavioral_extract",
    bash_command=f"{PY} pipeline.game_rec.data.behavioral_extract --out {OUT}",
)

task_id는 UI와 로그에 뜨는 이름이고 bash_command가 실제로 실행되는 명령이다.

의존성

extract >> ease >> validate
extract >> catalog
[validate, catalog] >> smoke

>>는 "왼쪽이 성공하면 오른쪽"이다. 그림으로 옮기면 이렇게 된다.

behavioral_extract ──┬─▶ build_ease_artifact ──▶ p5_validate ──┐
                     │                                         ├──▶ p5_smoke
                     └─▶ build_catalog_db ─────────────────────┘

ease와 catalog가 갈라지는 이유는 둘 다 extract 산출물만 필요하고 서로를 안 보기 때문이다. smoke는 EASE 텐서와 카탈로그 파일을 둘 다 읽어야 해서 양쪽을 기다린다. bat 파일로는 표현할 수 없는 부분이다.

trigger_rule

기본값은 all_success다. 앞 태스크가 전부 성공해야 실행된다. p5_validate가 게이트로 작동하는 것이 이 규칙 덕분이다. 품질 검증이 실패하면 p5_smoke는 upstream_failed가 되어 아예 돌지 않는다.

값실행 조건
all_success앞이 전부 성공 (기본값)
all_done앞이 전부 끝나기만 하면. 성공/실패 무관. 정리 작업용
one_failed앞 중 하나라도 실패하면. 알림 태스크용
none_failed실패가 없으면. 건너뛴 것은 허용
always무조건

파라미터를 명시한 이유

ease = BashOperator(
    task_id="build_ease_artifact",
    bash_command=(
        f"{PY} pipeline.game_rec.data.build_ease_artifact "
        f"--artifacts {OUT} --cap 12000 --topk 2048"
    ),
)

스크립트의 실제 기본값은 --topk 512인데, 게이트가 고른 프로덕션 값은 2048이다. 512와 1024는 p5_validate의 절단 손실 허용치를 통과하지 못했다. 라이브 산출물의 meta.json도 2048이다.

docs/operations.md §7은 2048을 "기본값"이라고 적어놨지만 코드 기본값은 512다. 프로덕션 빌드는 명시적으로 넘겼던 것으로 보인다. 문서 쪽 정정이 필요하다.

7. 스케줄링

cron 표기

schedule="0 12 * * *"은 분 시 일 월 요일 순서다. 매일 12:00 UTC. 한국 시간으로는 21:00이다. 컨테이너 안이 UTC라는 것을 잊으면 9시간 어긋난다.

표기의미
0 12 * * *매일 12:00
*/15 * * * *15분마다
0 9 * * 1매주 월요일 09:00
@daily0 0 * * *의 별칭
None자동 실행 없음. 수동 트리거 전용

logical_date는 실행 시각이 아니다

예전 이름이 execution_date라 더 헷갈렸다. 이것은 "이 실행이 담당하는 데이터 구간의 시작"이다. 매일 도는 DAG가 8월 2일 12시에 뜨면 logical_date는 8월 1일이다. 8월 1일치 데이터를 처리하는 실행이기 때문이다.

우리가 트리거한 실행에 data_interval_start 2026-07-31 12:00, data_interval_end 2026-08-01 12:00이 찍힌 것이 이 규칙이다.

catchup

초보자가 제일 크게 데는 부분이다. start_date를 과거로 잡고 catchup=True(기본값)로 두면, Airflow가 start_date부터 지금까지의 모든 스케줄을 소급해서 실행한다. start_date를 1년 전으로 적어놓고 켰다가 365개 실행이 한꺼번에 쏟아지는 사고가 흔하다. False면 앞으로 것만 돈다.

과거 구간을 일부러 돌리고 싶을 때는 catchup을 켜는 대신 backfill 명령을 쓴다. 

airflow dags backfill p5_rebuild -s 2026-07-01 -e 2026-07-07

max_active_runs

이 DAG의 실행이 동시에 두 개 이상 뜨지 않게 한다. 우리 태스크들은 outputs/p5/interactions.pkl 같은 고정 경로로 파일을 주고받기 때문에, 실행 두 개가 겹치면 서로의 중간 파일을 덮어쓴다. 실행이 스케줄 간격보다 길어질 때 조용히 깨지는 종류의 사고다.

실측으로 이 DAG는 성공 구간만 17분 가까이 걸린다. 하루 한 번 스케줄이면 여유가 크지만, 데이터가 늘어 실행이 24시간을 넘기 시작하면 이 설정이 방어선이 된다.

나머지 동작은 따로 유발해서 확인

위 사고는 "재시도가 소진되는" 경우만 보여줬다. 재시도로 복구되는 경우, 타임아웃, trigger_rule 변경은 안 보여줬으므로 dags/behavior_probe.py로 따로 확인했다. echo와 sleep뿐이고 파이프라인과 무관하다.

태스크설정관측

flaky는 Jinja 템플릿으로 시도 횟수를 읽어 첫 시도에만 실패한다. 템플릿이 bash_command에서 쓸 수 있다는 것 자체가 알아둘 만하다. 

bash_command=(
    "if [ {{ ti.try_number }} -lt 2 ]; then"
    "  echo \"attempt {{ ti.try_number }}: simulated transient failure\"; exit 1;"
    "fi; echo \"attempt {{ ti.try_number }}: recovered\""
)

재시도가 항상 좋은 것은 아니다

두 실패 모두 "파일이 없다"는 결정론적 오류인데 3번씩 돌았다. 1분 간격이라 헛되이 4분을 썼다. 재시도는 네트워크 오류나 API 스로틀 같은 일시적 실패에만 의미가 있다. 입력 누락처럼 몇 번을 다시 해도 같은 결과가 나오는 실패에는 해롭기만 하다.

Airflow는 이 둘을 구분하지 못한다. 사람이 정해줘야 한다. 방법은 둘이다.

  • 태스크별로 retries=0을 준다. 입력 존재 여부에 좌우되는 태스크에 맞다.
  • 스크립트가 AirflowFailException을 던지게 한다. 이 예외는 재시도를 건너뛰고 바로 실패로 간다.

재시도 안전성은 Airflow가 보장하지 않는다

이건 우리 스크립트의 성질이다. 이 DAG의 태스크들은 매번 산출물을 통째로 덮어쓰므로 몇 번을 다시 돌려도 결과가 같다. 반면 기존 값에 더하는 종류의 태스크라면 재시도할 때마다 값이 부풀어 오른다. 재시도를 켜기 전에 이걸 먼저 판단해야 한다.

크롤 태스크를 아직 DAG에 넣지 않은 이유이기도 하다. 크롤러는 자체 예산 게이트와 재개 커서를 갖고 있어서 재개 자체는 안전하지만, 컨테이너에서 실제 DB에 쓰는 경로가 위험해서 별도 결정이 필요하다.

9. 태스크 사이의 데이터 전달

처음 쓰면 반드시 막히는 지점이다. 태스크는 각각 별개의 프로세스다. 실무에서는 아예 다른 머신일 수도 있다. 그래서 파이썬 변수를 공유할 수 없다.

XCom

Airflow 메타DB를 통해 값을 주고받는다. 파일 경로, 개수, 플래그 같은 작은 메타데이터용이다. 메타DB에 저장되므로 큰 데이터를 넣으면 DB가 터진다. 

# 보내는 쪽
def count_users(**ctx):
    return 23347                      # 반환값이 자동으로 XCom에 저장된다

# 받는 쪽
def report(**ctx):
    n = ctx["ti"].xcom_pull(task_ids="count_users")

공유 스토리지

앞 태스크가 파일로 쓰고 뒤 태스크가 읽는다. 큰 산출물은 이쪽이 정석이다. behavioral_extract가 남긴 것들이다. 

outputs/p5/interactions.pkl     205 MB
outputs/p5/game_stats.pkl        10 MB
outputs/p5/user_stats.pkl       1.5 MB
outputs/p5/pool.json            348 KB
outputs/p5/extract_stats.json   378 B

build_ease_artifact가 --artifacts /opt/project/outputs/p5로 이것을 읽는다. XCom을 안 쓴 게 아니라, 205MB짜리를 XCom에 넣으면 안 되기 때문에 못 쓰는 것이다.

11. 직접 고쳐보기

DAG 파일을 고쳤을 때

재시작할 필요가 없다. 스케줄러가 15초마다 폴더를 다시 읽는다. 문법 오류가 있으면 UI 상단에 배너가 뜨고 명령으로도 확인된다.

태스크 하나만 테스트

docker compose exec airflow-scheduler \

태스크 추가

예를 들어 재빌드 전에 DB 상태를 찍어두는 단계를 넣는다면 이렇게 된다.

재시도 정책 바꾸기

catalog = BashOperator(
    task_id="build_catalog_db",
    bash_command=...,
    retries=0,                  # default_args를 태스크 단위로 덮어쓴다
)

실패한 태스크만 다시 돌리기

UI에서 실패한 네모를 클릭하고 Clear를 누르면 그 태스크와 하위가 다시 큐에 들어간다. 앞 단계는 다시 안 돈다. 11분짜리 추출을 다시 돌리지 않아도 되는 것이 이 구조의 실익이다. 명령으로도 된다. 

docker compose exec airflow-scheduler \
  airflow tasks clear p5_rebuild -t build_catalog_db -s 2026-08-02 -e 2026-08-02

일시정지와 해제

새로 만든 DAG는 멈춤 상태로 시작한다. compose에 AIRFLOW__CORE__DAGS_ARE_PAUSED_AT_CREATION: 'true'를 넣어둔 안전장치다. 파일을 저장하자마자 스케줄이 돌기 시작하는 사고를 막는다. 

airflow dags unpause p5_rebuild
airflow dags pause p5_rebuild

13. 자주 막히는 곳

DAG가 UI에 안 보인다

  1. dags list-import-errors로 문법 오류를 먼저 본다.
  2. 파일이 airflow_lab/dags/에 있는지, 컨테이너 안 /opt/airflow/dags에 보이는지 확인한다.
  3. 15초를 기다린다. 폴더 스캔 주기다.
  4. 파일 안에 DAG 객체가 최상위 스코프에 있어야 한다. 함수 안에서 만들면 안 잡힌다.

DAG는 보이는데 안 돈다

  • 일시정지 상태인지 확인한다. UI 왼쪽 토글.
  • start_date가 미래면 안 돈다.
  • catchup=False인데 아직 첫 스케줄 시각이 안 왔으면 안 돈다. 수동 트리거로 확인한다.

DAG 파싱이 느리다

스케줄러가 15초마다 DAG 파일을 통째로 실행해서 DAG 객체를 만든다. 파일 맨 위에 DB 조회나 큰 파일 읽기를 넣으면 그게 15초마다 돈다. 무거운 일은 반드시 태스크 안에 들어가야 한다.

태스크가 파일을 못 찾는다

컨테이너 안 경로와 호스트 경로가 다르다. 호스트의 D:\...\Game_recommendation\outputs\p5는 컨테이너에서 /opt/project/outputs/p5다. DAG에는 항상 컨테이너 경로를 쓴다.

권한 오류

Read-only file system이 뜨면 read-only 마운트 영역에 쓰려는 것이다. 의도한 방어일 수도 있고 경로를 잘못 잡은 것일 수도 있다. 4절의 마운트 표를 확인한다.

14. 실제로 겪은 문제들

Docker 백엔드가 반복해서 죽음

이미지를 받는 도중 com.docker.backend.exe가 세 번 연속 죽었다. 디스크와 메모리를 의심했지만 둘 다 아니었다. docker 데이터 디스크에 944GB가 남아 있었고 VM 커널 로그에 OOM 흔적이 없었다.

원인은 %LOCALAPPDATA%\Docker\log\host\monitor.log에 있었다. 

unexpected fault address 0xffffffffffffffff
fatal error: fault
[signal 0xc0000005 code=0x0 addr=0xffffffffffffffff pc=0x3329b95]

goroutine 4287 [running]:
gvisor.dev/gvisor/pkg/tcpip/transport/tcp.(*endpoint).sendTCP
runtime: g 4287: unexpected return pc for ...sendTCP called from 0x4

Docker Desktop의 gVisor 사용자공간 TCP 스택이 송신 경로에서 액세스 위반을 냈다. 직전 로그에 동시 TCP 연결이 12개까지 열려 있었고, 그게 멀티 레이어 이미지 pull이 만드는 부하다.

조치는 동시 다운로드 수를 1로 줄이는 것이었다. %USERPROFILE%\.docker\daemon.json에 넣는다. 

{
  "builder": { "gc": { "defaultKeepStorage": "20GB", "enabled": true } },
  "experimental": false,
  "max-concurrent-downloads": 1
}

그 뒤 pull과 빌드가 통과했다. 다만 같은 재시작에서 Docker Desktop이 28.3.0에서 29.6.2로 자동 업데이트됐다. 설정과 버전 두 가지가 동시에 바뀌었으므로 어느 쪽이 해결했는지는 단정할 수 없다.

백엔드가 죽은 상태에서는 Settings 화면의 Apply & Restart가 동작하지 않는다. connect ENOENT \\.\pipe\dockerBackendApiServer가 뜨고 편집 내용이 저장되지 않는다. 그럴 때는 daemon.json을 직접 고치고 Docker Desktop을 완전히 종료 후 재실행한다.

대용량 SQLite를 마운트 너머로 읽는 비용

behavioral_extract가 user_achievement 950만 행을 읽는 데 컨테이너에서 314.2초와 283.6초가 걸렸다. 같은 단계가 호스트에서 구 DB(550만 행) 기준으로는 13.1초와 6.8초였다. 행 수는 1.7배인데 시간은 20배가 넘는다.

DB 크기와 실행 환경이 동시에 다르므로 마운트 비용만 분리해 측정한 값은 아니다. 다만 태스크 전체가 11분 09초 걸렸고 그중 10분이 이 두 읽기였다는 사실은 그대로다.

문서와 코드가 어긋난 곳

build_catalog_db.py의 모듈 docstring은 인구도 사전 파일에 대해 missing -> eps floor라고 적어놨다. 실제 190번 줄은 이렇다. 

rates = json.loads(args.pop.read_text())

폴백이 구현되어 있지 않다. 파일이 없으면 FileNotFoundError로 죽는다. 문서만 믿었다면 원인을 찾는 데 한참 걸렸을 것이다.

게이트 태스크가 로컬 전용 파일에 의존

p5_validate는 experiments/p6_ood/p6_panels.json을 읽는다. 동결된 P6 평가 패널인데, 이 파일은 raw SteamID를 담고 있어 2026-07-22에 gitignore 처리됐다. 클론한 리포에는 없다는 뜻이고, 다른 머신이나 CI에서는 이 게이트가 돌지 않는다.

수집 태스크

크롤을 이 DAG에 넣으려면 컨테이너 밖에서 실행시켜야 한다. WAL SQLite에 9p 너머로 쓰는 것이 금지선이기 때문이다. 선택지는 둘이다.

  • SSHOperator로 호스트에서 실행. Windows에 OpenSSH Server 설치가 필요하고 관리자 권한이 든다.
  • 크롤은 기존 로컬 스케줄러에 두고 Airflow는 재빌드 배치만 맡는다. 예산 게이트와 재개 커서를 자체 보유한 상시 데몬은 원래 Airflow가 감쌀 형태가 아니라는 점에서 방어된다.

크롤을 바운디드 일일 슬라이스로 바꾸는 것 자체는 코드 수정 없이 된다. --stop-at-users가 누적 총량 기준이므로 DAG에서 현재 카운트에 N을 더해 넘기면 되고, --seed-today로 예산 게이트도 이어붙일 수 있다.
